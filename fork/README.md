# Fork notes: "Always Show" custom formats (Sonarr v5)

This fork of [Sonarr/Sonarr](https://github.com/Sonarr/Sonarr) carries one small
feature on top of the exact release we run in Docker. This file is the map for
future-us: what the patch does, where it lives, how to move it to the next
release, and how to build and ship the image.

This is the **v5** line of the fork, started from the first public v5 beta. The
v4 line lives on `feature/always-show-custom-formats` (based on `v4.0.19.2979`)
and still owns the `latest` image tag; see "Branching model" below.

## What the feature does

- Every custom format inside a Quality Profile gets an **Always Show** checkbox
  (Settings > Profiles > edit profile > Custom Formats, next to the score).
- On a series page, an episode row shows the checked formats that actually
  match the episode's file as small tags at the right edge of the title cell.
  Nothing shows for episodes without a file or without a matching format, and
  the tags step aside while the (hidden by default) Formats column is visible,
  because that column already lists every matching format.
- Nothing else changes. Scoring is untouched and there is no language-specific
  logic. The flag is generic and works with any custom format.

## Design notes worth remembering

- **No database migration.** `FormatItems` is stored as one JSON column, so the
  new bool just appears in that JSON. Old rows deserialize with `false`.
  Rolling back to stock Sonarr is safe: the unknown key is ignored and dropped
  on the next save.
- **The episode row recalculates nothing.** The file's `customFormats` are
  already computed by the API, and the quality profiles are already cached by
  react-query (`useQualityProfiles`). The row only intersects the two lists.
- **`alwaysShow` is nullable on both APIs on purpose.** Tools like Recyclarr
  PUT whole profiles (through V3) without knowing about the field. When an item
  arrives without it, `Update` copies the stored value instead of resetting it
  to false. The web UI always sends an explicit value, so unticking still works.
- `openapi.json` is generated upstream; we edited both copies by hand to keep
  the diff honest. The `*.module.css.d.ts` typings are not committed in v5
  (gitignored, generated by `yarn types:css`), so nothing to hand-edit there.
- Only `en.json` has the new strings. Other UI languages fall back to English
  for those two keys.

## Branching model

- `origin` is `mandave98/Sonarr`, `upstream` is `Sonarr/Sonarr` (fetch only; its
  push URL is disabled in the local clone). The fork on GitHub carries none of
  upstream's v5 tags: `git fetch upstream --tags` is what gives a local clone
  the tag names used below, and the workflow fetches them from upstream on its
  own.
- Upstream branches since the v5 beta: `develop` is v5, `v4-develop` is v4
  maintenance, `main` is the v4 stable line. v5 builds are tagged
  `v5.0.0.<build>` on `develop` and published as GitHub pre-releases; the
  release feed channel is `v5-nightly`:

  ```bash
  curl -s http://services.sonarr.tv/v1/releases | jq -r '."v5-nightly".version'
  ```

- Beware: the upstream repository also carries stray tags with Radarr version
  numbers (`v4.7.x`, `v5.2x.x`, `v6.x.x`) that point at Radarr commits. Ignore
  them; only `v5.0.0.*` (and whatever v5.x follows) are Sonarr's. `git
  describe` is unaffected because those commits are not in our history.
- This branch, `v5/always-show-custom-formats`, is based on tag `v5.0.0.2785`,
  the first public v5 beta (the tip of `upstream/develop` on 2026-10-24).
  LinuxServer ships that version as `develop-version-5.0.0.2785` (also
  `develop`), so the branch is again "the binary we run plus the patch".
- The v4 branch `feature/always-show-custom-formats` is untouched and keeps
  publishing `latest`. Once v5 runs for real we can retire it.

Moving to the next v5 build, tag to tag:

```bash
git fetch upstream --tags
git checkout v5/always-show-custom-formats
git rebase --onto v5.0.0.NNNN v5.0.0.2785
# fix conflicts if any (see hotspots below), then
git push --force-with-lease origin v5/always-show-custom-formats
```

Then update the version defaults in `fork/Dockerfile` (`BASE_IMAGE`,
`SONARR_VERSION`) and `fork/build-image.sh`, replace `5.0.0.2785` in this
file, rebuild, and redeploy. When LinuxServer moves v5 to their stable
`latest`, switch `LSIO_TAG_PREFIX` in the workflow from `develop-version-` to
`version-` and the `BASE_IMAGE` defaults likewise.

Likely conflict hotspots when rebasing: `en.json` (huge, alphabetical, churns
constantly), both `openapi.json` files (regenerated by an upstream bot),
`EditQualityProfileModalContent.tsx` if upstream reworks the profile editor,
`EpisodeRow.tsx` (upstream has an `episode-details-redesign` branch in flight),
and `fork/build.sh` whenever `.github/actions/build/action.yml` changes. All of
them are a few lines to re-apply.

## Building the image

Requirements: Docker with BuildKit. No local .NET or Node needed; the build
stage uses `node:24.19.0-bookworm` (Node 24.19.0 and Yarn 1.22.22, the volta
pins in `package.json`) and installs the exact .NET SDK that `global.json` pins
(10.0.402 at this tag).

Upstream dropped `build.sh` in v5; its CI builds through
`.github/actions/build/action.yml` plus the frontend job in
`.github/workflows/build_v5.yml`. `fork/build.sh` mirrors those steps for
`linux-musl-x64` / `net10.0`: stamp the version into `src/Directory.Build.props`,
`yarn install && yarn build` (Vite, into `_output/UI`), `dotnet msbuild ...
-t:PublishAllRids`, then package `_artifacts/linux-musl-x64/net10.0/Sonarr`
with `UI/` inside, the same layout the LinuxServer image unpacks into
`/app/sonarr/bin`. Diff it against the upstream action after each rebase.

**The SDK pin is not cosmetic.** On v4 a newer patch SDK produced an image that
crashed on startup because the self-contained publish shipped a different
`System.Text.Encoding.CodePages.dll` than `Sonarr.deps.json` expected. Keep
`DOTNET_SDK_VERSION` equal to `global.json`; `build-image.sh` and the workflow
read it from there automatically.

```bash
fork/build-image.sh                       # -> sonarr-fork:5.0.0.2785
SONARR_VERSION=5.0.0.2800 fork/build-image.sh
```

What it does:

1. Build stage on `node:24.19.0-bookworm` + .NET 10 SDK, running `fork/build.sh`.
2. Starts from the stock LinuxServer image for the same version and replaces
   only `/app/sonarr/bin` with the packaged folder. `Sonarr.Update` is removed
   and `package_info` is rewritten exactly like the LinuxServer Dockerfile does
   (`Branch=develop`, `PackageVersion=<version>-fork-<sha>`), so in-app updates
   stay disabled and System > Status shows the fork as the package source.

Build from a real clone, not from a git worktree: SourceLink runs during the
build and needs the `.git` directory inside the build context (a worktree only
has a `.git` pointer file, which the container cannot follow). Warnings are
errors in the upstream build, so a missing repository fails the build.

Expect the first build to take a while (full .NET restore for .NET 10, `yarn
install`, Vite). Later builds reuse the toolchain layers but redo the source
build whenever anything in the repo changes. The build context includes `.git`
on purpose, see above.

The image is roughly twice the size of the stock one because the stock
`/app/sonarr/bin` layer is still underneath ours. Harmless, just not pretty.

### Published automatically

`.github/workflows/fork-image.yml` builds the same Dockerfile on every push to
`v5/always-show-custom-formats` (and on manual dispatch) and pushes it to
GitHub Container Registry as:

- `ghcr.io/mandave98/sonarr-fork:<sonarr version>`
- `ghcr.io/mandave98/sonarr-fork:<sonarr version>-<short sha>`
- `ghcr.io/mandave98/sonarr-fork:v5`

It never touches `latest`; that tag still means the v4 build from the other
branch, so the production compose file keeps working until we decide to move.
The Sonarr version comes from `git describe` against upstream's v5 tags, which
the workflow fetches from Sonarr/Sonarr itself because the fork does not carry
them. It refuses to publish anything but a 5.x version: the first run on this
branch resolved an ancient v4 tag the fork happened to have, built with that
version stamped in, and pushed a mislabeled image. The SDK version comes from
`global.json`. A rebase therefore needs no edits to the workflow. The test
stage runs first; a failing test blocks the push.
Upstream's own workflows only trigger on `develop` and `main`, so they stay
idle on this branch.

The workflow uses no Actions cache, on purpose (measured on v4: restoring the
toolchain from cache saved about ten seconds, exporting it cost six minutes and
gigabytes per run). The publish step does not compile twice either: it reuses
the build stage from the builder's own state within the job.

The package inherits the repository's visibility, and this fork is public, so
the tags pull anonymously from any host.

To push a locally built image by hand instead:

```bash
docker tag sonarr-fork:5.0.0.2785 ghcr.io/mandave98/sonarr-fork:5.0.0.2785
docker push ghcr.io/mandave98/sonarr-fork:5.0.0.2785   # after docker login ghcr.io
```

## Deploying

v5 is a beta and its database migrations are one-way. **Take a v4 backup first**
(System > Backup) and keep it; going back means restoring that backup into a v4
container. Then swap the image and keep everything else:

```yaml
services:
  sonarr:
    image: ghcr.io/mandave98/sonarr-fork:v5   # was ghcr.io/mandave98/sonarr-fork:latest
    # same environment, volumes and ports as before
```

The `/config` volume is reused and migrated on first start. Going back to the
v4 fork or to the LinuxServer image is the image line plus the restored backup.

## Verifying a build

Backend unit tests run from the published test assemblies, on musl, the same
way upstream CI runs them. The `test` stage in `fork/Dockerfile` does that:

```bash
docker build -f fork/Dockerfile --target test .
# everything instead of the fork-focused subset:
docker build -f fork/Dockerfile --target test --build-arg TEST_FILTER="Category!=ManualTest&Category!=WINDOWS&Category!=IntegrationTest&Category!=AutomationTest" .
```

Do not run `dotnet test` against the `.csproj` files directly. Without the
solution context `stylecop.json` is not picked up, so hundreds of unrelated
StyleCop warnings become errors and nothing builds.

Frontend checks can run on the host when its Node matches the volta pin
(24.19.0), which it currently does:

```bash
npx yarn@1.22.22 install --frozen-lockfile
npx yarn@1.22.22 lint
npx yarn@1.22.22 typecheck      # generates the css typings, then tsc
npx yarn@1.22.22 stylelint
```

The same commands work inside the build stage image
(`docker build -f fork/Dockerfile --target build -t sonarr-fork-build:dev .`).
At this tag all three pass with the fork applied; the v4-era stylelint crash is
gone.

`fork/smoke-test.sh <image>` starts a throwaway container from the built image
and drives the API end to end on both versions: the container boots and reports
the fork package info, the two new translation strings are served, a custom
format is created, the profile picks it up with `alwaysShow: false`, a V5 PUT
with `true` sticks and is visible through V3, V3 and V5 PUTs that omit the
field (what Recyclarr sends) keep `true`, and an explicit `false` clears it.
It needs docker, curl and node; see the header of the script for the Windows
Git Bash incantation.

Manual check after deploying:

1. Settings > Profiles > edit a profile, tick **Always Show** on a format,
   save. Reopen the profile; the tick must still be there.
2. Open a series using that profile. Episodes whose file matches the format
   show the tag at the right edge of the title cell.
3. `GET /api/v5/qualityprofile` (and `/api/v3/qualityprofile`) lists
   `"alwaysShow": true` on that item.
4. If Recyclarr is in use, run a sync and repeat step 1. The tick must survive.
